# ActiVibe — Instruksi untuk Claude

## Design System (WAJIB DIBACA SEBELUM EDIT UI/STYLE)

Semua styling (warna, font, spacing, radius, komponen) di seluruh aplikasi — landing page, dashboard Volunteer, Organizer, maupun Admin — **wajib mengikuti [docs/design.md](docs/design.md)**. Dokumen itu adalah rujukan tunggal untuk keputusan visual.

Sebelum menambah atau mengubah style:
- Jangan hardcode hex warna baru di komponen — pakai CSS custom property (`var(--token-name)`) yang sudah didefinisikan di `docs/design.md` Section 1.
- Kalau butuh warna yang tidak ada di palet resmi, **berhenti dan tanya dulu ke user**, jangan menebak hex sendiri.
- Section gap konsisten 40-48px (`--space-section-gap`), radius card besar 20px (12px khusus table density di dashboard Organizer/Admin), font heading = Itim, font body = Poppins.
- Dashboard Organizer dan Admin pakai token yang **identik** dengan Volunteer — yang boleh beda hanya density layout, bukan bahasa visualnya (lihat Section 8 di `docs/design.md`).
- Cek checklist di Section 9 `docs/design.md` sebelum menambahkan warna/style baru.

## Struktur Repo

Monorepo dengan 3 bagian utama:
- `frontend/` — Web app (React 19 + TypeScript + Vite, pakai `pnpm`)
- `backend/` — API & services (Express.js + PostgreSQL + Prisma + JWT — lihat [backend/README.md](backend/README.md)). Register & Login (`/auth/register`, `/auth/login`, `/auth/me`, `/auth/logout`) sudah dibangun & diverifikasi end-to-end, termasuk OTP (FR-002/003, lihat Section "Verifikasi OTP & Tiket Event" di bawah). Auth dipanggil langsung dari frontend lewat REST API (`fetch`, `credentials: 'include'`), **bukan** Next.js/NextAuth — token disimpan sebagai httpOnly cookie, frontend tidak pegang token mentah (lihat `frontend/src/contexts/AuthContext.tsx`).
- `docs/` — Dokumentasi product (PRD, design system, dst.). Untuk setup env var email (Resend) yang konsisten lintas-PC, lihat [docs/EMAIL_SETUP.md](docs/EMAIL_SETUP.md) — `backend/.env` sengaja gitignored jadi tidak ikut sinkron lewat git.

Lihat [README.md](README.md) dan [docs/PRD-ActiVibe-v2.0.md](docs/PRD-ActiVibe-v2.0.md) untuk detail produk lengkap. Untuk requirement detail dashboard Organizer/NGO (role & shift, pipeline applicant, attendance, close-event flow, dst — FR-028 s.d. FR-052), lihat addendum [docs/PRD-ActiVibe-v2.1-Organizer-Addendum.md](docs/PRD-ActiVibe-v2.1-Organizer-Addendum.md).

**Routing:** `frontend/` pakai `react-router-dom` (dikonfigurasi di `frontend/src/routes/AppRoutes.tsx`, dibungkus `<BrowserRouter>` di `App.tsx`). Routing terbagi 2 grup nested route lewat layout wrapper (`<Outlet />`): `PublicLayout` (dipakai `/`, `/tentang-kami`, `/cara-kerja`) dan `DashboardLayout` (dipakai `/dashboard`, dan jadi pola yang akan dipakai ulang untuk dashboard Organizer/Admin nanti). Topbar-nya sendiri ada di komponen bersama `AppTopbar` (`frontend/src/components/AppTopbar.tsx`) — logo, nav link, mega-menu "Cari Aktivitas"/"Cari Organisasi", dropdown notifikasi & user, hamburger mobile. `DashboardLayout` selalu render `AppTopbar`; `PublicLayout` render `AppTopbar` juga TAPI HANYA kalau `user` (dari `useAuth()`) sudah login — kalau belum login (atau masih `isLoading`), `PublicLayout` render `Navbar` marketing biasa (Masuk/Daftar) sebagai gantinya. Jadi begitu user login, navbar-nya konsisten "dashboard-style" di halaman publik manapun, bukan cuma di `/dashboard`. `AuthModal` tetap di `App.tsx` di luar kedua layout (state modal lintas-halaman). Kalau menambah halaman publik baru, daftarkan di bawah `PublicLayout` di `AppRoutes.tsx`; kalau halaman dashboard baru, di bawah `DashboardLayout` (atau layout dashboard role lain kalau sudah dibuat).

## Personalisasi AI (FR-005) — `backend/src/modules/recommendations/`

Endpoint `GET /recommendations` (auth cookie) menghasilkan daftar event dengan **Predictive Match Score** dua lapis:

1. **Rule-based** (`matchScore.js`) — bobot: skill 40%, minat 30%, motivasi 15% (dikunci di `backend/README.md`, jangan diubah sepihak), availability 10%, lokasi 5%. Data profil yang belum diisi dinilai netral 50% (tidak menghukum profil belum lengkap). Ada unit test `matchScore.test.js`.
2. **Layer AI multi-provider** (`ai.service.js` = orkestrator; implementasi per mesin di `providers/`: Claude `claude-opus-4-8`, ChatGPT/OpenAI default `gpt-4o-mini`, Gemini default `gemini-2.5-flash` — semua pakai structured/JSON output dengan schema yang sama) — memberi rating final (maks ±10 poin dari skor rule-based, di-clamp server), `matchReasoning` 1 kalimat, `fitBadgeLabel`, dan `symbol` emoji. Pemilihan mesin lewat env `AI_PROVIDER` (`claude|openai|gemini|auto`; `auto` = provider pertama yang API key-nya terisi, urutan claude → openai → gemini). Kalau tidak ada key / API error, otomatis fallback ke rule-based + reasoning template (`aiGenerated: false`, `aiProvider: null`) — flow tidak pernah gagal karena AI. API key semua provider hanya di `backend/.env` (gitignored), JANGAN pernah di-hardcode atau di-commit.

**Data event sudah nyata** (bukan dummy lagi, sejak 2026-07-05): `recommendation.service.js` mengambil katalog dari `listMatchableEvents()` di `event.service.js` (query `Event` status PUBLISHED/ONGOING + `EventSkill`/`EventInterest` join, dipetakan ke shape yang sama dgn dulu dipakai `DUMMY_EVENTS`). `matchScore.js`/`ai.service.js` tidak berubah sama sekali — keduanya fungsi murni yang tidak peduli asal data. Event butuh `category`, `eventSkills`, `eventInterests`, `motivationTags`, `dayType` terisi supaya skornya tidak netral 50% terus (skill 40% + interest 30% = 70% bobot algoritma) — organizer mengisi ini lewat field tagging di `CreateEventPage.tsx` (kategori + skill/interest multi-select + motivasi + waktu pelaksanaan, semua opsional), dan `backend/prisma/seed.js` sudah mengisi tag untuk 8 event demo `evt-1`..`evt-8`.

Client frontend: `frontend/src/services/recommendation.service.ts` (fetch + `credentials: 'include'`, pola sama dengan `lib/api.ts`). Dashboard volunteer (`FindActivityPage`) pakai hook `frontend/src/hooks/useRecommendations.ts`: hook memetakan response API ke tipe `Event` UI — field presentasi yang belum ada di API (foto, rating, ulasan, profil organizer, kebijakan) diisi default generik netral (BUKAN di-merge dari mock data lagi). Kalau fetch gagal, hook mengembalikan `error: string` (tidak lagi diam-diam fallback ke mock) — halaman menampilkan `SectionState` (lihat Section "Error Handling" di bawah). Simbol emoji hasil AI tampil di badge Match Score card (`EventListSidebar`) dan fit badge panel detail; baris status di bawah jumlah hasil menunjukkan apakah personalisasi AI aktif. **Alur pasca-onboarding:** selesai wizard `OnboardingModal`, `DashboardLayout` menampilkan `PersonalizationResultModal` **2 tahap** sebelum user dilepas ke dashboard: Card 1 = hasil analisis AI (narasi hobi/jurusan/minat → `analysis.recommendedRole` + lokasi, plus grafik bar afinitas kategori dari `analysis.chart` — dihitung deterministik di backend, bukan oleh AI); Card 2 = top-3 kegiatan + CTA "Daftar Sekarang" → navigate `/dashboard?event=<id>`. **Aturan tier kecocokan (keputusan produk, sumber tunggal: `getRelevance()` di backend `recommendation.service.js`):** 0–49 "Kurang Cocok", 50–79 "Sedikit Relevan", 80–100 "Sangat Relevan & Cocok" — frontend menampilkan `relevanceLabel` dari API apa adanya; `utils/matchScore.ts` memetakan ambang yang sama ke warna badge (success/info/warning). Hasil fetch di-cache module-level (TTL 5 menit + dedupe in-flight) di `recommendation.service.ts` — panggil `invalidateRecommendations()` setiap profil berubah. Backend melewati panggilan AI kalau profil belum punya sinyal apa pun (belum onboarding) supaya dashboard cepat.

**Behavioral boost (sinyal "buka"/"simpan" event)** — `backend/src/modules/recommendations/behavior.service.js`: `getBehavioralAffinity(userId)` membaca riwayat `EventView` (bobot 1) dan `EventBookmark` (bobot 3, "suka" eksplisit lebih berat dari sekadar buka) milik user, dipetakan ke tag kategori/minat. `behaviorBoost(event, affinityMap)` — fungsi murni (unit test `behavior.service.test.js`, pola sama `matchScore.test.js`) — mengembalikan penyesuaian **0..+10** (BUKAN ±10 spt clamp AI: event tanpa overlap dapat 0, bukan dihukum negatif, karena kekurangan overlap sudah tercermin di skor rule-based). Boost ini ditambahkan ke `matchScore` final di `recommendation.service.js` dan diekspos sbg field `behaviorBoost` di tiap item `recommendations` (auditable). **TIDAK mengubah `WEIGHTS` di `matchScore.js`** (tetap dikunci sesuai `backend/README.md`) — ini post-adjustment terpisah, pola sama dgn clamp ±10 milik `ai.service.js`. Cold-start (user baru, belum ada `EventView`/`EventBookmark`) otomatis dapat boost 0 di semua event, fallback bersih ke rule-based+AI biasa.

## Endpoint Volunteer-Facing (Public Read) — `backend/src/modules/events/`

Sebelumnya `event.routes.js` mengunci **seluruh router** ke `requireRole('ORGANIZER')` — tidak ada endpoint publik untuk volunteer melihat event. Sejak 2026-07-05 ditambahkan (didaftarkan **sebelum** `router.use(requireRole('ORGANIZER'))` di file yang sama, karena middleware level-router di Express cuma berlaku utk route yang didaftarkan setelahnya):
- `GET /events/public` — daftar event `status` PUBLISHED/ONGOING (filter opsional `keyword`/`category`/`location`/`skill`), dipetakan lewat `serializePublicEvent()` (bentuk volunteer-facing, BEDA dari `serializeEvent()` yang organizer-shaped/roles-requirements).
- `GET /events/public/:id` — detail satu event publik.
- `POST /events/:id/view`, `POST` & `DELETE /events/:id/bookmark`, `GET /events/bookmarks/me` — tracking perilaku (lihat behavioral boost di atas) + fitur simpan/like, semua `requireAuth` saja (bukan role-restricted).

`listMatchableEvents()` (dipakai `recommendation.service.js`) dan `listPublishedEventsForVolunteer()` (dipakai endpoint `/public`) adalah fungsi yang sama — satu sumber query, jangan duplikasi.

## Domain Organisasi — `backend/src/modules/organizations/`

Model Prisma `Organization` (2026-07-05, direvisi 2026-07-08): sejak 2026-07-08 satu User bisa memiliki **lebih dari satu** Organization (`ownerId` TIDAK unique lagi — kalau butuh relasi User→org, `User.organizations` sekarang array, bukan objek tunggal). Ada dua jalur pembuatan Organization yang terpisah:
1. **Auto-provision** (sejak 2026-07-05, tidak berubah): `ensureOrganizationForOwner()` dipanggil dari `event.service.js` `createEvent()` — organizer yang bikin event pertama kali langsung dapat Organization dengan `status: ACTIVE`, tanpa email/aktivasi. `frontend/src/pages/organizer/organization-views/*` masih 100% hardcoded/statis, belum tersambung ke model ini.
2. **Form self-service "Daftarkan Organisasimu"** (baru 2026-07-08): menu di `AppTopbar` dropdown "Cari Organisasi" → `frontend/src/pages/volunteer/OrganizationRegisterPage.tsx` (route `/dashboard/organisasi/daftar`), bisa diisi user role apapun (tidak harus sudah ORGANIZER). Submit → `POST /organizations/register` (`requireAuth` saja) via `organization.service.js` `registerOrganization()`: Organization dibuat `status: PENDING_VERIFICATION` + token aktivasi (di-hash pakai `utils/hash.js`, sama seperti RefreshToken, expiry 24 jam), lalu email dikirim lewat `utils/mailer.js` (wrapper `resend`, ada di `backend/package.json` tapi baru benar2 dipakai di sini — kalau `RESEND_API_KEY` kosong, link aktivasi di-log ke console alih2 gagal, pola fail-soft sama seperti AI provider). Klik link → `GET /organizations/activate?token=...` (sengaja TANPA `requireAuth`, token sendiri buktinya) → `activateOrganization()`: `status` jadi `ACTIVE` + `User.role` di-upgrade ke `ORGANIZER` kalau belum, lalu redirect ke `ORGANIZER_PORTAL_URL` (env baru, default `http://localhost:5174`, portal organizer = build frontend terpisah). Redirect lintas-portal ini aman tanpa re-login karena cookie auth host-only ke domain backend (bukan ke origin frontend) dan `requireAuth`/`requireRole` selalu re-fetch role dari DB tiap request (lihat `getUserFromAccessToken`), bukan dari klaim JWT lama. Satu user boleh mendaftarkan >1 organisasi (masing2 independen soal status aktivasi). Belum ada UI "kelola organisasi saya" (list punya user) atau tombol resend-email — di luar scope saat ini.

Endpoint: `GET /organizations` (list + filter `name`/`location`/`causeArea`), `GET /organizations/:id` — keduanya `requireAuth` saja, dipakai `FindOrganizationPage` (frontend: `frontend/src/lib/organizationApi.ts`), dan **keduanya cuma menampilkan organisasi `status: ACTIVE`** (organisasi `PENDING_VERIFICATION` belum pantas muncul di direktori publik). `eventsCount` dihitung server-side dari event `PUBLISHED`+`ONGOING`+`COMPLETED` milik organisasi tsb — jangan hitung ulang di frontend. `rating` belum ada fitur ulasan organisasi, sengaja dikembalikan `0` (netral, bukan angka karangan) sampai fitur itu dibangun. Statistik admin (`admin.service.js` `getUnverifiedOrganizationCount`, `getRegionDistribution`) juga sudah disaring ke `status: ACTIVE` supaya organisasi yang masih pending tidak ikut kehitung sbg entitas nyata.

## Verifikasi OTP Registrasi (FR-002/003) & Tiket Event dengan QR (FR-006/007, FR-044) — 2026-07-08

**OTP registrasi.** Model Prisma `OtpRequest`/`OtpPurpose` sudah ada sejak migration pertama tapi baru benar2 dipakai sekarang. `registerUser()` (`backend/src/modules/auth/auth.service.js`) tidak lagi langsung membuat sesi: user dibuat `isVerified: false`, kode OTP 6 digit di-hash (`utils/hash.js`, pola sama refresh token) & disimpan sbg `OtpRequest` (`expiresAt` dari `env.OTP_EXPIRY_MINUTES`, default 5 menit), dikirim via `sendOtpEmail()` (`utils/mailer.js`, fail-soft ke console.log kalau `RESEND_API_KEY` kosong — pola sama email aktivasi organisasi). Endpoint baru: `POST /auth/verify-otp` (cocokkan kode, kalau benar baru `issueTokens()` + set cookie — sesi baru terbit di titik ini, BUKAN saat `/auth/register`) dan `POST /auth/resend-otp` (dibatasi `env.OTP_MAX_RESEND_ATTEMPTS`, default 3, dihitung dari total baris `OtpRequest` yang pernah dibuat utk user+purpose itu). `loginUser()` menolak akun `isVerified: false` (403) — konsisten dgn cek `SUSPENDED`/`INACTIVE` yang sudah ada, ditaruh setelah cek password supaya tidak bisa dipakai enumerasi akun. Registrasi ulang dgn email yang sama tapi belum diverifikasi TIDAK di-409, melainkan meng-update baris User yg sama & kirim ulang OTP (supaya user yang menutup tab sebelum verifikasi bisa retry). Frontend: `frontend/src/components/OtpVerifyForm.tsx` (komponen bersama, dipakai `AuthModal.tsx` utk volunteer & `pages/auth/SignupPage.tsx` utk portal Organizer/Admin) — `AuthContext.register()` sekarang HANYA mengembalikan `{ email }` (bukan login otomatis), sesi baru ke-set lewat `verifyOtp()`.

**Tiket event dengan QR (FR-006/007) & check-in via kode tiket (FR-044).** `Application` (`backend/prisma/schema.prisma`) punya kolom `ticketCode` (nullable — tetap `null` sampai volunteer diterima, bukan cuma "Application lama sebelum fitur ini"). Alur direvisi 2026-07-08: `applyToEvent()` (`backend/src/modules/applications/application.service.js`) TIDAK LAGI generate ticketCode/QR saat apply — cuma membuat `Application` (`status: APPLIED`) dan mengirim email konfirmasi "sedang ditinjau" via `sendApplicationPendingEmail()` (fire-and-forget). `ticketCode` + QR baru diterbitkan di `updateApplicationStatus()` saat organizer mengubah status jadi `ACCEPTED` (sekali saja — dicek `!application.ticketCode` supaya tidak generate ulang kalau di-update lagi), lalu dikirim via `sendEventTicketEmail()` (fire-and-forget, kegagalan kirim email tidak menggagalkan perubahan status). Ini sengaja supaya applicant yang `REJECTED`/`WAITLISTED` tidak pernah punya tiket check-in yang valid. QR di email di-attach sbg **inline attachment (`content_id` CID)**, BUKAN `data:` URI di `<img src>` — Gmail dkk. memblokir/strip `data:` URI di email HTML sehingga QR tidak pernah tampil kalau di-inline langsung (`QRCode.toBuffer()`, bukan `toDataURL()`). `EventApplyForm.tsx` pasca-submit hanya menampilkan kartu "Menunggu konfirmasi" (tanpa QR — memang belum ada tiket di titik ini); tiket+QR cuma ada di email begitu diterima, belum ada halaman "lihat tiketku" di app. Check-in: `POST /applications/ticket/check-in` (`checkInByTicketCode()`, role ORGANIZER) mencari `Application` langsung dari `ticketCode` — BEDA dari `checkInAssignment()` yang sudah ada sebelumnya (butuh `VolunteerAssignment`/role+shift) — supaya event yang tidak pakai role/shift (opsional per event) tetap bisa di-check-in. **Keterbatasan yang disengaja:** hasil check-in via tiket meng-update `Application.status` (langsung kelihatan di badge pipeline applicant), tapi TIDAK otomatis muncul di tabel roster `AttendancePage.tsx` (`attendanceRecords`, yg keyed by `VolunteerAssignment`) kalau applicant itu belum di-assign ke shift manapun — organizer input kode tiket lewat field teks di halaman itu (`checkInByTicket()` di `OrganizerDataContext.tsx`), bukan scanner kamera (belum dibangun, potensi follow-up).

## Error Handling Per-Section (Volunteer Pages)

Sebelumnya tidak ada pola error/empty state yang konsisten (ada 2 gaya ad hoc berbeda + `useRecommendations` diam-diam mengganti data asli dengan mock kalau fetch gagal, tanpa pesan error apa pun). Sejak 2026-07-05: **`frontend/src/components/SectionState.tsx`** adalah komponen bersama untuk 3 state (`variant="error"|"empty"|"loading"`, styling dari `docs/design.md` Section 6.2 card + Section 1.7 token warna semantik) — dipakai di semua halaman volunteer (`FindActivityPage`, `FindOrganizationPage`, `ApplicationHistoryPage`, `SavedItemsPage`) menggantikan pola lama. **`frontend/src/components/SectionErrorBoundary.tsx`** (class component, `componentDidCatch`) membungkus render `EventDetailPanel`/`OrganizationDetailPanel` sbg pertahanan tambahan terhadap error saat render (bukan cuma error fetch) — supaya kalau satu section gagal, cuma section itu yang menampilkan error, bukan seluruh halaman. Pola untuk hook data-fetching: JANGAN diam-diam fallback ke data lain seolah sukses (`isFallback` lama) — selalu simpan `error: string | null` di state hook dan biarkan halaman render `SectionState` apa adanya.

## Git Commit & Push

Jangan pernah menjalankan `git commit` atau `git push` (lewat tool apa pun) di sesi utama tanpa diminta eksplisit oleh user di pesan itu juga. Cukup siapkan perubahan di working tree (`git add` boleh, atau tidak sama sekali), lalu biarkan user yang melakukan commit & push sendiri.

**Pengecualian (dikonfirmasi user 2026-06-22):** kalau user secara eksplisit memilih menjalankan `superpowers:subagent-driven-development` (atau skill lain yang mekanismenya butuh commit antar-task untuk diff review), implementer **subagent** boleh commit lokal per task sebagai mekanisme internal proses — bukan final history. Tidak ada `git push` dalam kondisi apa pun. User tetap pegang kendali penuh untuk review/reset/squash semua commit itu sebelum push sendiri. Di luar konteks ini (misal menulis spec/plan doc biasa di sesi utama), tetap jangan commit tanpa diminta.
