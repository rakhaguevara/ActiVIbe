## Design System (WAJIB DIBACA SEBELUM EDIT UI/STYLE)

Semua styling (warna, font, spacing, radius, komponen) di seluruh aplikasi — landing page, dashboard Volunteer, Organizer, maupun Admin — **wajib mengikuti [docs/design.md](docs/design.md)**. Dokumen itu adalah rujukan tunggal untuk keputusan visual.

Sebelum menambah atau mengubah style:
- Jangan hardcode hex warna baru di komponen — pakai CSS custom property (`var(--token-name)`) yang sudah didefinisikan di `docs/design.md` Section 1.
- Kalau butuh warna yang tidak ada di palet resmi, **berhenti dan tanya dulu ke user**, jangan menebak hex sendiri.
- Section gap konsisten 40-48px (`--space-section-gap`), radius card besar 20px (12px khusus table density di dashboard Organizer/Admin), font heading = Itim, font body = Poppins.
- Dashboard Organizer dan Admin pakai token yang **identik** dengan Volunteer — yang boleh beda hanya density layout, bukan bahasa visualnya (lihat Section 8 di `docs/design.md`).
- Cek checklist di Section 9 `docs/design.md` sebelum menambahkan warna/style baru.

## Personalisasi AI (FR-005) — `backend/src/modules/recommendations/`

Endpoint `GET /recommendations` (auth cookie) menghasilkan daftar event dengan **Predictive Match Score** dua lapis:

1. **Rule-based** (`matchScore.js`) — bobot: skill 40%, minat 30%, motivasi 15% (dikunci di `backend/README.md`, jangan diubah sepihak), availability 10%, lokasi 5%. Data profil yang belum diisi dinilai netral 50% (tidak menghukum profil belum lengkap). Ada unit test `matchScore.test.js`.
2. **Layer AI multi-provider** (`ai.service.js` = orkestrator; implementasi per mesin di `providers/`: Claude `claude-opus-4-8`, ChatGPT/OpenAI default `gpt-4o-mini`, Gemini default `gemini-2.5-flash` — semua pakai structured/JSON output dengan schema yang sama) — memberi rating final (maks ±10 poin dari skor rule-based, di-clamp server), `matchReasoning` 1 kalimat, `fitBadgeLabel`, dan `symbol` emoji. Pemilihan mesin lewat env `AI_PROVIDER` (`claude|openai|gemini|auto`; `auto` = provider pertama yang API key-nya terisi, urutan claude → openai → gemini). Kalau tidak ada key / API error, otomatis fallback ke rule-based + reasoning template (`aiGenerated: false`, `aiProvider: null`) — flow tidak pernah gagal karena AI. API key semua provider hanya di `backend/.env` (gitignored), JANGAN pernah di-hardcode atau di-commit.

**Data event sudah nyata** (bukan dummy lagi, sejak 2026-07-05): `recommendation.service.js` mengambil katalog dari `listMatchableEvents()` di `event.service.js` (query `Event` status PUBLISHED/ONGOING + `EventSkill`/`EventInterest` join, dipetakan ke shape yang sama dgn dulu dipakai `DUMMY_EVENTS`). `matchScore.js`/`ai.service.js` tidak berubah sama sekali — keduanya fungsi murni yang tidak peduli asal data. Event butuh `category`, `eventSkills`, `eventInterests`, `motivationTags`, `dayType` terisi supaya skornya tidak netral 50% terus (skill 40% + interest 30% = 70% bobot algoritma) — organizer mengisi ini lewat field tagging di `CreateEventPage.tsx` (kategori + skill/interest multi-select + motivasi + waktu pelaksanaan, semua opsional), dan `backend/prisma/seed.js` sudah mengisi tag untuk 8 event demo `evt-1`..`evt-8`.

Client frontend: `frontend/src/services/recommendation.service.ts` (fetch + `credentials: 'include'`, pola sama dengan `lib/api.ts`). Dashboard volunteer (`FindActivityPage`) pakai hook `frontend/src/hooks/useRecommendations.ts`: hook memetakan response API ke tipe `Event` UI — field presentasi yang belum ada di API (foto, rating, ulasan, profil organizer, kebijakan) diisi default generik netral (BUKAN di-merge dari mock data lagi). Kalau fetch gagal, hook mengembalikan `error: string` (tidak lagi diam-diam fallback ke mock) — halaman menampilkan `SectionState` (lihat Section "Error Handling" di bawah). Simbol emoji hasil AI tampil di badge Match Score card (`EventListSidebar`) dan fit badge panel detail; baris status di bawah jumlah hasil menunjukkan apakah personalisasi AI aktif. **Alur pasca-onboarding:** selesai wizard `OnboardingModal`, `DashboardLayout` menampilkan `PersonalizationResultModal` **2 tahap** sebelum user dilepas ke dashboard: Card 1 = hasil analisis AI (narasi hobi/jurusan/minat → `analysis.recommendedRole` + lokasi, plus grafik bar afinitas kategori dari `analysis.chart` — dihitung deterministik di backend, bukan oleh AI); Card 2 = top-3 kegiatan + CTA "Daftar Sekarang" → navigate `/dashboard?event=<id>`. **Aturan tier kecocokan (keputusan produk, sumber tunggal: `getRelevance()` di backend `recommendation.service.js`):** 0–49 "Kurang Cocok", 50–79 "Sedikit Relevan", 80–100 "Sangat Relevan & Cocok" — frontend menampilkan `relevanceLabel` dari API apa adanya; `utils/matchScore.ts` memetakan ambang yang sama ke warna badge (success/info/warning). Hasil fetch di-cache module-level (TTL 5 menit + dedupe in-flight) di `recommendation.service.ts` — panggil `invalidateRecommendations()` setiap profil berubah. Backend melewati panggilan AI kalau profil belum punya sinyal apa pun (belum onboarding) supaya dashboard cepat.

**Behavioral boost (sinyal "buka"/"simpan" event)** — `backend/src/modules/recommendations/behavior.service.js`: `getBehavioralAffinity(userId)` membaca riwayat `EventView` (bobot 1) dan `EventBookmark` (bobot 3, "suka" eksplisit lebih berat dari sekadar buka) milik user, dipetakan ke tag kategori/minat. `behaviorBoost(event, affinityMap)` — fungsi murni (unit test `behavior.service.test.js`, pola sama `matchScore.test.js`) — mengembalikan penyesuaian **0..+10** (BUKAN ±10 spt clamp AI: event tanpa overlap dapat 0, bukan dihukum negatif, karena kekurangan overlap sudah tercermin di skor rule-based). Boost ini ditambahkan ke `matchScore` final di `recommendation.service.js` dan diekspos sbg field `behaviorBoost` di tiap item `recommendations` (auditable). **TIDAK mengubah `WEIGHTS` di `matchScore.js`** (tetap dikunci sesuai `backend/README.md`) — ini post-adjustment terpisah, pola sama dgn clamp ±10 milik `ai.service.js`. Cold-start (user baru, belum ada `EventView`/`EventBookmark`) otomatis dapat boost 0 di semua event, fallback bersih ke rule-based+AI biasa.

## Fitur "Women Respect" (info keamanan/kenyamanan peserta perempuan) — 2026-07-09

Terinspirasi gerbong khusus wanita KAI. `Profile.gender` (`Gender` enum: `MALE`/`FEMALE`, nullable di DB — pola sama `motivation`/`availability`) ditambahkan ke schema. **Wajib diisi, dikumpulkan di 2 titik berlapis (bukan cuma satu):**
1. **`AuthModal.tsx`** (form registrasi volunteer, satu-satunya jalur self-signup — lihat Section "Portal Organizer & Admin login-only") — dropdown `<select>` wajib di form signup, pola sama `LocationSelector`: belum ada sesi saat `register()` dipanggil, jadi ditahan di state lokal `gender` lalu dikirim via `updateMyProfile({ gender })` di `handleOtpVerified()` begitu OTP terverifikasi (bareng `location` kalau ada, satu PATCH).
2. **`OnboardingModal.tsx`** (fallback) — kalau user entah bagaimana sampai ke wizard onboarding TANPA `initialProfile.gender` terisi (mis. akun lama, atau AuthModal gagal kirim), chat step 0 otomatis mulai dari pertanyaan gender (quick-reply, `chatPhase` mulai dari `'gender'`) SEBELUM pertanyaan bio. Kalau `initialProfile.gender` sudah ada, langkah ini di-skip total (`startingChatPhase`/`startingBotMessage` di awal komponen menentukan mulai dari `'gender'` atau langsung `'bio'`) — user TIDAK PERNAH ditanya dua kali.

User yang sudah pernah onboarding SEBELUM fitur ini ada (jadi `gender` masih `null` dan tidak lewat AuthModal versi baru) bisa isi belakangan lewat section baru "Jenis Kelamin" di `SettingsPage.tsx` (pola sama section "Ketersediaan" di halaman yang sama, real `updateMyProfile({ gender })`).

Di `event.service.js`, `serializePublicEvent()` (dipakai `listPublishedEventsForVolunteer`/`getPublishedEventById`, jadi ikut mengalir ke `listMatchableEvents()` → `recommendation.service.js` → `/recommendations`) mengembalikan 2 field tambahan:
- `organizerGender` — `event.organizer.profile?.gender`. "Pembina" = organizer/pembuat event (`Event.organizerId`), TIDAK ada konsep PIC lapangan terpisah di data model.
- `femaleAcceptedCount` — jumlah `Application` dgn `status` `ACCEPTED`/`CHECKED_IN`/`COMPLETED` (bukan semua yg APPLIED — keputusan produk supaya angkanya cerminan siapa yg benar-benar akan hadir) milik user ber-`gender: FEMALE`, dihitung via `femaleAcceptedCountByEventId()` (mirror pola `filledSlotsByEventId()`).

`recommendation.service.js` meneruskan kedua field ini secara eksplisit (objek `recommendations` di sana di-whitelist manual, bukan spread — field baru harus ditambah manual tiap kali nambah field baru di `serializePublicEvent`).

Frontend: tiap halaman yang menampilkan event (list/swipe/detail/simpan) fetch `getMyProfile()` sendiri-sendiri (state lokal `currentUserGender` — BELUM ada context/hook bersama utk ini, sengaja duplikasi pola simple `useEffect` per halaman drpd bikin abstraksi baru utk 1 field), diteruskan sbg prop `currentUserGender` ke komponen card/form di bawahnya. Badge `👩 {femaleAcceptedCount} perempuan terdaftar` muncul di **4 tempat**: `EventListSidebar` (card list), `SwipeDeck`/`SwipeCard` (mode swipe), `EventDetailPanel` (panel detail, baris `.event-detail-panel__badges` sejajar match score badge), `SavedItemsPage` (grid kegiatan tersimpan) — semua di-wire dari `FindActivityPage.tsx` KECUALI `SavedItemsPage` (halaman sendiri) dan `ActivityDetailPage.tsx` (route detail mobile `/dashboard/activity/:id`, fetch `getMyProfile()` sendiri juga). `EventApplyForm` (halaman pendaftaran) dapat banner lebih lengkap (jumlah peserta + gender pembina), bukan cuma badge. **Semua tempat ini SENGAJA cuma render kalau `currentUserGender === 'FEMALE'`** — tidak pernah tampil ke user MALE/belum isi gender. Styling badge/banner pakai token `--color-secondary-soft`/`--color-secondary-dark` (kategori "info netral" di `docs/design.md` — TIDAK ada token pink di palet resmi, jangan bikin token baru tanpa tanya user). Kalau nanti nambah lagi permukaan card event baru, ikuti pola yang sama — jangan lupa wire `currentUserGender`-nya, gampang kelewat.

## Domain Organisasi — `backend/src/modules/organizations/`

Model Prisma `Organization` (2026-07-05, direvisi 2026-07-08): sejak 2026-07-08 satu User bisa memiliki **lebih dari satu** Organization (`ownerId` TIDAK unique lagi — kalau butuh relasi User→org, `User.organizations` sekarang array, bukan objek tunggal). Ada dua jalur pembuatan Organization yang terpisah:
1. **Auto-provision** (sejak 2026-07-05, tidak berubah): `ensureOrganizationForOwner()` dipanggil dari `event.service.js` `createEvent()` — organizer yang bikin event pertama kali langsung dapat Organization dengan `status: ACTIVE`, tanpa email/aktivasi. `frontend/src/pages/organizer/organization-views/*` masih 100% hardcoded/statis, belum tersambung ke model ini.
2. **Form self-service "Daftarkan Organisasimu"** (baru 2026-07-08, **disatukan jadi 1 alur set-password+OTP 2026-07-09** — sebelumnya ada 2 jalur beda tergantung status login, sekarang login state saat submit **tidak relevan sama sekali**): menu di `AppTopbar` dropdown "Cari Organisasi" → `frontend/src/pages/volunteer/OrganizationRegisterPage.tsx` (route `/dashboard/organisasi/daftar`, field `contactName` SELALU wajib diisi — beda dari revisi sebelumnya yang menyembunyikannya kalau sudah login). Submit → `POST /organizations/register` (**TANPA `requireAuth`**, tidak ada optional-auth check apapun lagi) via `organization.service.js` `registerOrganization(payload)`:
   - `resolveOwner(payload)`: kalau `User` dengan email organisasi itu sudah ada (verified ataupun belum), dipakai apa adanya sbg owner (password/role-nya TIDAK disentuh di titik ini). Kalau belum ada, `User` baru dibuat dengan password placeholder acak + `isVerified: false`.
   - Organization dibuat `status: PENDING_VERIFICATION` + token aktivasi (di-hash pakai `utils/hash.js`, expiry 24 jam), lalu **satu-satunya** email dikirim: `sendOrganizationSetPasswordEmail` berisi link ke `frontend/src/pages/volunteer/SetOrganizationPasswordPage.tsx` (route publik `/set-password-organisasi?token=...`, di bawah `PublicLayout`).

   **`SetOrganizationPasswordPage.tsx`** — satu halaman, wizard 3 langkah (state lokal `step`, tidak pakai route terpisah per langkah):
   1. Isi password + konfirmasi (divalidasi client-side, TIDAK dikirim ke server dulu) → `POST /organizations/set-password/request-otp` `{token}` → `requestOrganizationActivationOtp()`: generate kode OTP 6 digit, simpan sbg `OtpRequest` (purpose baru `ORGANIZATION_ACTIVATION`, keyed ke `owner.id` — model/pola sama dgn OTP registrasi FR-002/003 di `auth.service.js`, cuma purpose beda), kirim via `sendOrganizationActivationOtpEmail`.
   2. Isi kode OTP → `POST /organizations/set-password` `{token, password, code}` (password dikirim ULANG dari state form, bukan dari langkah 1 — server tidak menyimpan apapun di antara langkah 1 & 2) → `verifyOrganizationActivationOtp()`: verifikasi kode (hash cocok, belum expired, `attempts < 5` — mekanisme sama seperti `verifyRegistrationOtp`), begitu cocok baru dalam SATU transaksi: `User.password` di-hash+simpan, `isVerified: true`, role naik ke `ORGANIZER` kalau belum, `Organization.status` jadi `ACTIVE`. **Sengaja tidak menolak kalau owner sudah `isVerified` sebelumnya** (skenario: email organisasi ini kebetulan sudah jadi akun ActiVibe existing, atau daftar >1 organisasi dgn email sama) — OTP-lah yang jadi gate pembuktian pemilik email, jadi password TETAP diganti sesuai yang baru diisi (setara alur "reset password via email" yang gated OTP, bukan lubang keamanan).
   3. Kartu "Selesai!" → link ke `PORTAL_URLS.ORGANIZER` (frontend, `config/portalUrls.ts`) utk login manual pakai email+password yang baru diatur. **Tidak auto-login lintas-portal** (halaman ini di origin volunteer/5173, tujuan akhirnya organizer portal/5174 — beda origin, sengaja tidak dipaksa share sesi cross-port).

   `generateOtpCode()` sekarang di `utils/otp.js` (diekstrak dari `auth.service.js` supaya tidak duplikasi antara OTP registrasi & OTP aktivasi organisasi). Endpoint lama `GET /organizations/activate` (aktivasi tanpa password, dipakai kalau submit sambil login) **sudah dihapus total**, begitu juga `sendOrganizationActivationEmail` dan env var `BACKEND_URL`/`ORGANIZER_PORTAL_URL` yang cuma dipakai di sana.

   Satu user boleh mendaftarkan >1 organisasi (masing2 independen soal status aktivasi/token). Belum ada UI "kelola organisasi saya" (list punya user) — di luar scope saat ini.

**Portal Organizer & Admin login-only** (2026-07-09): halaman signup mandiri (`SignupPage.tsx`, route `/daftar`, link "Belum punya akun? Daftar" di `LoginPage.tsx` lewat prop `showSignupLink`) **dihapus total** dari kedua portal — satu-satunya jalan jadi organizer sekarang lewat alur "Daftarkan Organisasimu" di atas. `LoginPage.tsx` tidak lagi punya prop `showSignupLink`.

## Verifikasi OTP Registrasi (FR-002/003) & Tiket Event dengan QR (FR-006/007, FR-044) — 2026-07-08

**OTP registrasi.** Model Prisma `OtpRequest`/`OtpPurpose` sudah ada sejak migration pertama tapi baru benar2 dipakai sekarang. `registerUser()` (`backend/src/modules/auth/auth.service.js`) tidak lagi langsung membuat sesi: user dibuat `isVerified: false`, kode OTP 6 digit di-hash (`utils/hash.js`, pola sama refresh token) & disimpan sbg `OtpRequest` (`expiresAt` dari `env.OTP_EXPIRY_MINUTES`, default 5 menit), dikirim via `sendOtpEmail()` (`utils/mailer.js`, fail-soft ke console.log kalau `RESEND_API_KEY` kosong — pola sama email aktivasi organisasi). Endpoint baru: `POST /auth/verify-otp` (cocokkan kode, kalau benar baru `issueTokens()` + set cookie — sesi baru terbit di titik ini, BUKAN saat `/auth/register`) dan `POST /auth/resend-otp` (dibatasi `env.OTP_MAX_RESEND_ATTEMPTS`, default 3, dihitung dari total baris `OtpRequest` yang pernah dibuat utk user+purpose itu). `loginUser()` menolak akun `isVerified: false` (403) — konsisten dgn cek `SUSPENDED`/`INACTIVE` yang sudah ada, ditaruh setelah cek password supaya tidak bisa dipakai enumerasi akun. Registrasi ulang dgn email yang sama tapi belum diverifikasi TIDAK di-409, melainkan meng-update baris User yg sama & kirim ulang OTP (supaya user yang menutup tab sebelum verifikasi bisa retry). Frontend: `frontend/src/components/OtpVerifyForm.tsx` (komponen bersama, dipakai `AuthModal.tsx` utk volunteer & `pages/auth/SignupPage.tsx` utk portal Organizer/Admin) — `AuthContext.register()` sekarang HANYA mengembalikan `{ email }` (bukan login otomatis), sesi baru ke-set lewat `verifyOtp()`.

**Tiket event dengan QR (FR-006/007) & check-in via kode tiket (FR-044).** `Application` (`backend/prisma/schema.prisma`) punya kolom `ticketCode` (nullable — tetap `null` sampai volunteer diterima, bukan cuma "Application lama sebelum fitur ini"). Alur direvisi 2026-07-08: `applyToEvent()` (`backend/src/modules/applications/application.service.js`) TIDAK LAGI generate ticketCode/QR saat apply — cuma membuat `Application` (`status: APPLIED`) dan mengirim email konfirmasi "sedang ditinjau" via `sendApplicationPendingEmail()` (fire-and-forget). `ticketCode` + QR baru diterbitkan di `updateApplicationStatus()` saat organizer mengubah status jadi `ACCEPTED` (sekali saja — dicek `!application.ticketCode` supaya tidak generate ulang kalau di-update lagi), lalu dikirim via `sendEventTicketEmail()` (fire-and-forget, kegagalan kirim email tidak menggagalkan perubahan status). Ini sengaja supaya applicant yang `REJECTED`/`WAITLISTED` tidak pernah punya tiket check-in yang valid.
